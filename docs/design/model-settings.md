# Model Configuration Design

This document defines model configuration, credential bindings and preferences. See [validation status](../validation.md) for current evidence.

## Open configuration contract

New configurations use OpenAI Responses or Anthropic Messages. Add and Edit share one custom form with no presets, vendor field, model catalog or Advanced section. Model IDs are entered manually without an allowlist. All models offer exactly Off, Low, Medium and High; the user is responsible for model/parameter compatibility. Off is an explicit disable request, not omission or a provider default. The app neither clamps effort nor falls back to another protocol, model or output mode after a rejection.

Keep the native grouped form and draft/Save/Cancel transaction. Show exactly six fields in this order: Name, Protocol, Model ID, Reasoning Effort, API Base URL and API key. Protocol and effort are single-choice pickers. A new sheet starts with empty name, model ID, Base URL and key fields; users type these values themselves. Protocol defaults to OpenAI and effort to Low. Switching either picker never fills the text fields. The API key remains masked and optional at save time. Editing loads the saved fields and retains the existing key status/replace/delete controls. Existing vendor labels and private request options remain stored for compatibility but have no editor controls.

OpenAI appends `responses` to the Base URL; Anthropic appends `v1/messages`. A full request URL override is used literally without automatic path completion. Preserve path prefixes and ports. HTTPS, URL syntax and credential-destination checks still apply. Authentication supports Bearer, x-api-key, a custom header name, and no authentication. Header values and API keys belong in the configuration-scoped Keychain item, never preferences, portable documents or logs. A protocol, destination or authentication-binding change invalidates inherited credentials; a display-only vendor rename does not.

The protocol defaults map OpenAI effort to `reasoning.effort` (`none` for Off); Anthropic Off sends `thinking.type: disabled`, and Low/Medium/High send adaptive thinking with `output_config.effort`. These are request conventions, not model support claims. Retained additional JSON can override optional generation parameters. App-owned model identity, input/system messages, tools, streaming and output schema cannot be replaced through additional JSON. The simplified editor does not author additional JSON. JSON must be an object with unique keys and finite numbers. No hidden retries, tools, environment-derived credentials or redirects are introduced.

Output mode is explicit: prompt-constrained JSON, native JSON Object where represented by the selected protocol, or native JSON Schema. All responses still pass the canonical local schema, unit coverage and span checks. Anthropic has no JSON Object wire mode: choose prompt-constrained JSON or JSON Schema. Optional sampling is omitted when blank, preserving the distinction from zero. Token caps are positive bounded integers and are separate for translation and alignment.

Versioned open profiles carry optional request options through preferences and the app/worker pair. Runtime bindings freeze the complete private connection/options snapshot; portable documents retain only a nonsecret configuration revision identifier in addition to existing attribution. Reopening requires an explicitly selected matching saved configuration. Editing a connection cannot mutate an existing task's parameters or redirect its credentials.

Existing v1/v2 profiles, credentials, IDs, active selection and retained task attribution remain readable and preserve their exact request behavior. Confirming an edit to a legacy entry converts it to the chosen open protocol. Legacy effort outside the four supported editor values requires an explicit choice rather than silently becoming Off. Cancelling or saving unrelated settings leaves legacy records unchanged.

The legacy capability mapping below remains only for retained v1/v2 profiles. Its model restrictions do not apply to the open profiles.

This document owns model configuration, retained capability mapping and migration. [Interaction](interaction.md) owns the toolbar and translation direction. [Native design](technical-design.md) owns scheduling and persistence transactions. [Worker protocol](worker-protocol.md) and [document format](document-format.md) own their serialized fields.

## Settings entry and model management

Use one dedicated native settings window (`Window(id: "settings")`) and exactly one app-menu Settings command, with Command-comma. Its label is `Settings…` in English and `设置…` in Simplified Chinese; the window title is localized consistently. SwiftUI's automatic `Settings` scene installs its own app-menu item in addition to any `CommandGroup(replacing: .appSettings)` command — producing two `Settings…` entries, both bound to Command-comma — and the scene's automatic item follows the system locale, so it cannot honor the app's explicit interface language. The dedicated window keeps the single-entry contract, the Command-comma open-or-focus behavior in both window-focus states, the localized label and title, the close review, and Command-W routing.

Keep General, Models and Reading sections. In Models, put **Active Model** (`使用模型`) first, followed by the configured models and Add, Edit and Delete. The picker shows instance names and selects configurations by stable ID. Each configured model occupies one line with the instance name leading and the vendor, exact API model ID and localized effort in secondary text trailing. Keep full values available through accessibility and a hover tooltip. The row selected for editing is independent of Active Model. Exclude endpoints and credentials from rows and picker labels.

Add/Edit opens a native sheet. Sheet confirmation updates the Settings draft. Field-validation failures keep that draft and show a settings-validation message before any credential write; they must not be described as a Keychain failure. Settings Save commits the full draft, Cancel discards it, and closing a dirty window offers Save, Discard or Cancel. CRUD, protocol/effort selection and Settings Save are local. First addition to an empty list selects that entry. Other additions preserve selection. Deleting the active entry requires an explicit replacement if any entries remain. Deleting the last entry clears the selection. Explain that a deleted configuration can no longer supply a credential for undispatched work. A saved configuration without a key remains selectable and offers Settings when a job cannot dispatch.

The toolbar and saved Settings share one app-wide active ID. Toolbar changes persist immediately through the existing Settings store and can choose only committed entries. When Settings is open, refresh its active ID if that field has no explicit draft edit, preserving other unsaved edits. Keep a deliberately edited valid ID in the draft and show that Save will apply it. If a staged deletion makes the toolbar's newly selected ID unavailable in the draft, require a replacement before Save. Cancel leaves any committed toolbar change in effect. On persistence failure, show the prior committed selection and surface the error. This is a single preference, with no per-tab model selection.

## Configuration record and editor

Keep preferences schema 2 and the existing serialized `defaultModelConfigurationID` key as the active ID. Keep language, appearance and typography. Reading preferences include optional-on-read `preferredReadingWidth`, `preferredCorrespondenceColor` and `skipDocumentSavePrompt` fields; absent values resolve to Wide, Amber and false. They use the same draft transaction, with no schema bump, model/credential reset or portable-document fields. Explicitly saved color choices remain respected. Add an optional-on-read `preferredTranslationDirection` field using the existing direction values. Persist the translation direction preference described in [interaction](interaction.md#input-and-task-lifecycle). Each configuration keeps a stable UUID from Add through Edit. The six visible fields follow the order above.

Each configuration stores a stable UUID, optional display name, protocol/profile, exact model ID, one of the four efforts, canonical Base URL, private request options and a configuration revision UUID. The vendor label is optional in persistence and Save validation. Existing labels remain readable and are validated when present; new custom records omit the label and use the protocol label in list metadata. Protocol IDs are `openai` and `anthropic`; labels do not route requests. Trim display names with a 128-character single-line limit; blank display names retain the existing fallback to the model ID without prefilling the Name field. Model IDs remain single-line, trimmed, case-sensitive and at most 256 UTF-8 bytes.

Use the existing uniqueness rule for the resolved name/effort pair. Two instances can share an API model, endpoint or key. Name/model edits preserve unrelated fields and credentials. Protocol, final URL or authentication changes invalidate inherited credentials. Restoring the exact committed binding before Save restores its original key unless the user explicitly replaced or deleted it. A replacement typed for another binding never travels to a new destination.

Validate Base URLs locally: require a host and HTTPS; reject user information, query, fragment, whitespace/control characters and operation suffixes such as `/chat/completions`, `/responses` or `/messages`. The editor accepts Base URLs only; retained full request URL overrides remain an internal compatibility field. Preserve path prefixes and ports; normalize scheme/host casing and default HTTPS port. Base URLs end with one slash, while full request URLs preserve their path literally. New origins require the existing transmission acknowledgement, using the actual request destination.

Private request options use `endpointURL`, `authentication`, `headerName`, `apiVersion`, `outputMode`, `translationTokens`, `alignmentTokens`, optional `temperature` and `extraBodyJSON`. Defaults are prompt JSON, Bearer authentication, 16,384/4,096 output tokens, omitted temperature and empty additional JSON. Selecting Anthropic uses x-api-key authentication. Switching protocols updates the standard Bearer/x-api-key default; retained custom/no-auth selections remain unchanged. A protocol switch preserves name, model, URL, effort and generation settings. If retained options are incompatible with the selected protocol, Apply explains that the user must restore the original protocol or add a new custom configuration. Additional JSON is limited to 16 KiB; secret headers and key share the existing 4 KiB Keychain credential limit. Header names are ASCII tokens and values are printable ASCII. Reject duplicate header names regardless of case, control characters and reserved transport/authentication headers. Authentication and generation options have no controls in the simplified editor. Additional reasoning objects must remain objects; output format and app-owned task fields cannot be overwritten.

## Fresh preferences and custom connections

The Add sheet has no connection templates or suggestions. Users supply a model ID and Base URL compatible with the selected protocol; saving never discovers account models or sends a request. Fresh preferences still seed the existing OpenAI and GLM configurations. Persisted entries are not reseeded, and this editor change does not reset existing connections, credentials or task snapshots.

## Effort capabilities and wire mapping

This section documents retained v1/v2 Chat Completions behavior only. The editor always uses the four open-profile choices described above. Historical menus are not exposed by the new editor.

`auto` means provider/model default, not disabled reasoning. It omits graded `reasoning_effort`. `off` is an explicit request to disable reasoning; `on` enables binary thinking where no graded effort exists; `minimal` is the lowest graded level, offered only for models whose provider documents it. The model list uses Default, Off, On, Minimal, Low, Medium, High, Extra high and Max, with localized equivalents. For a known nonreasoning model, `auto` displays Not applicable and the editor disables effort selection.

Support the OpenAI, GLM, Kimi and DeepSeek capability entries below, including legacy entries used by existing configurations. Menus expose distinct documented settings for the selected model. Provider compatibility aliases that collapse to an existing level are represented by that level.

| Capability entry (checked 2026-11-05) | Allowed effort | v2 final body |
| --- | --- | --- |
| OpenAI `gpt-4.1-mini-2025-04-14` (deprecated; removal 2027-01-14) | `auto` only | Omit reasoning fields; `temperature: 0.2` |
| OpenAI `gpt-6-luna`, `gpt-6-sol`, `gpt-6.1-terra`, `gpt-5.6`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna` | `auto`, `off`, `low`, `medium`, `high`, `xhigh`, `max` | Off becomes `reasoning_effort: "none"`; a graded value is sent verbatim; Auto omits it. The GLM-5.3 entries cannot disable thinking and do not offer Minimal, Medium, On or Extra high; `reasoning_effort` itself is GLM-5.2-or-later only. Do not copy OpenAI's effort menu or unrelated capability clamping into these entries. Unknown model IDs may be saved and attempted once with Auto under the chosen v2 profile; omit model-specific thinking/sampling fields, use the conservative reasoning budget below, and report unsupported capabilities without another request. Explicit effort for an unknown model requires adding a documented capability entry and tests first. Capability metadata is local code, not an editable generic parameter dictionary.


The final serialized HTTP request must retain the configured URL, exact model, mapped effort, profile-specific output mode, token-limit field/cap, exact canonical messages, no tools and non-streaming operation. OpenAI v2 binds canonical strict JSON Schema. GLM, Kimi and DeepSeek v2 bind JSON-object output and validate against the canonical schema locally. Use `kimi-json-v2` and `deepseek-json-v2` as the new versioned profiles. SDK/LangChain mutation is `unsupported_capability` before HTTP. Never send `reasoning_content` as translated text or include it in document/log output.

Reasoning uses output budget as well as answer text. For known nonreasoning models and explicit Off, v2 uses 8,192 translation / 2,048 alignment tokens; both legacy profiles keep their original 4,096/1,024. Enabled, graded, Auto reasoning and unknown v2 entries use initial total caps of 16,384 translation / 4,096 alignment tokens. These bounded engineering starting values require evaluation and do not establish quality or latency guarantees. OpenAI and Kimi send `max_completion_tokens`. GLM and DeepSeek send only `max_tokens`. [Kimi Chat Completions reference](https://platform.kimi.com/docs/api/chat), [DeepSeek Chat Completions reference](https://api-docs.deepseek.com/api/create-chat-completion/). Keep existing input, decoded-output, unit-text, deadline, concurrency and no-retry limits. A length finish remains `output_limit`; do not parse partial JSON or silently increase a cap.

Preserve `openai-json-schema-v1` and `glm-json-v1` for retained jobs and migration compatibility, including their original fixed sampling/reasoning parameters. Their exact legacy rules remain in model workflow. New configurations and explicitly confirmed edits use the open profiles. Legacy tables remain executable for retained jobs only.

## Runtime snapshots, credentials and portable documents

At job creation, capture configuration ID, provider/profile, model ID, effort, canonical Base URL, full request options, configuration revision and prompt versions. Freeze the endpoint/effort for every translation batch and correspondence operation belonging to that job, including background work, Retry and Resume. Add effort and the private runtime binding identity to correspondence cache identity; explicit rebinding clears cached model analysis. Changing the active model or editing a configuration never silently retranslates or changes an existing snapshot.

Before each new dispatch, resolve that configuration's key and require the saved configuration still to exist with the exact frozen protocol, request URL and authentication identity. Perform the entry/URL check and credential read within the same serialized Settings transaction boundary. A model/effort/alias edit at the same endpoint does not mutate the old job, which keeps its original model/effort. Key rotation at the same URL applies to later dispatches; an already dispatched request keeps its original key. Deletion, a changed protocol, authentication or request endpoint blocks later dispatches with local `configuration_unavailable`, preserves completed work, and sends no key/request. Existing HTTP work may finish. Local retained jobs never rebind to a changed endpoint. Resume requires restoration of the original configuration/endpoint; another service requires explicit Retranslate with replacement confirmation and destination consent. Never select a similarly named/newly created entry automatically.

Portable files persist requested protocol/model/profile/effort, prompt attribution and a nonsecret configuration revision only. Saved open-profile configurations rotate that revision whenever effective request settings change; display-only edits retain it. They exclude endpoint, display alias, local configuration ID, Keychain reference and credentials. After Open, reading/export remains offline. Before Resume or uncached phrase analysis, require an explicit session-local binding to an existing configuration matching provider/model/profile/effort and, for open profiles, the configuration revision. Show its display name and destination host: a file intentionally cannot prove its original endpoint. No matching revision leaves model operations unavailable and offers restoring the original saved configuration or explicit Retranslate. Newly recreating identical fields produces a new revision and does not establish the original binding. This applies both to the initial analysis attempt and to a binding sheet whose candidates disappear before confirmation; keep the coarse correspondence fallback while explaining the missing configuration and offering Settings, explicit Retranslate, or Cancel. Retranslate retains its separate replacement confirmation. An explicit binding is required even when the active model matches. Do not mark a document dirty merely for this private runtime binding. The file-version details live in document format.

## Preferences and Keychain migration

Use `dev.bipara.preferences.v2` for the new encoded record. If it exists but is corrupt/newer, report the problem and preserve data rather than fall back to v1/defaults. Only when it is absent, migrate a valid `dev.bipara.preferences.v1` record once:

1. Create a fresh UUID entry for each existing OpenAI/GLM record, preserving its exact model ID, and use the original hardcoded Standard API URL. Preserve the old effective request profile: OpenAI v1 with Auto, GLM v1 with Off. Do not upgrade models, change to Coding Plan or add recommended entries during migration.
2. Map the old default provider to its new entry, and preserve language, appearance and typography. Malformed/missing provider/default data must produce a recoverable migration error rather than silently choosing an unrelated entry.
3. Read only the two legacy provider-scoped Keychain items through the existing credential interface. Stage independent configuration-scoped copies, then persist/read back the complete v2 preferences record through the Settings transaction. A missing key remains missing. Serialize credential reads with this transaction.
4. On failure, compensate staged writes and leave v1 authoritative and readable; report compensation failures. On success, v2 becomes authoritative. Cleanup of superseded legacy keys/record follows only after verified v2 persistence; cleanup failure reports residue, retains v2 and retries cleanup independently without repeating migration or generating new IDs.

Existing v2 records retain IDs, provider, endpoint, credentials, model, effort and selection on upgrade. A missing translation direction decodes as Automatic. Preserve persisted entries and empty-list behavior. Fresh-install seed entries and Add/Edit use the new open profiles. A rollback build may lack the new profiles or preference field, so exercise upgrade with the new app and its paired worker. Opening an existing portable file retains its recorded attribution. Files with new profile IDs remain readable on versions that support unavailable attribution, with execution requiring a recognized matching profile. Verify these cases against the [acceptance plan](../testing.md#settings-and-provider-acceptance).
