# Model Configuration Design

This document defines vendor/model configuration, credential bindings and preferences. See [validation status](../validation.md) for current evidence.

This document owns model configuration, catalog, capability mapping and migration. [Interaction](interaction.md) owns the toolbar and translation direction. [Native design](technical-design.md) owns scheduling and persistence transactions. [Worker protocol](worker-protocol.md) and [document format](document-format.md) own their serialized fields.

## Settings entry and model management

Use one dedicated native settings window (`Window(id: "settings")`) and exactly one app-menu Settings command, with Command-comma. Its label is `Settings…` in English and `设置…` in Simplified Chinese; the window title is localized consistently. SwiftUI's automatic `Settings` scene installs its own app-menu item in addition to any `CommandGroup(replacing: .appSettings)` command — producing two `Settings…` entries, both bound to Command-comma — and the scene's automatic item follows the system locale, so it cannot honor the app's explicit interface language. The dedicated window keeps the single-entry contract, the Command-comma open-or-focus behavior in both window-focus states, the localized label and title, the close review, and Command-W routing.

Keep General, Models and Reading sections. In Models, put **Active Model** (`使用模型`) first, followed by the configured models and Add, Edit and Delete. The picker shows instance names and selects configurations by stable ID. Each configured model occupies one line with the instance name leading and the vendor, exact API model ID and localized effort in secondary text trailing. Keep full values available through accessibility and a hover tooltip. The row selected for editing is independent of Active Model. Exclude endpoints and credentials from rows and picker labels.

Add/Edit opens a native sheet. Sheet confirmation updates the Settings draft. Settings Save commits the full draft, Cancel discards it, and closing a dirty window offers Save, Discard or Cancel. CRUD, catalog selection and Settings Save are local. First addition to an empty list selects that entry. Other additions preserve selection. Deleting the active entry requires an explicit replacement if any entries remain. Deleting the last entry clears the selection. Explain that a deleted configuration can no longer supply a credential for undispatched work. A saved configuration without a key remains selectable and offers Settings when a job cannot dispatch.

The toolbar and saved Settings share one app-wide active ID. Toolbar changes persist immediately through the existing Settings store and can choose only committed entries. When Settings is open, refresh its active ID if that field has no explicit draft edit, preserving other unsaved edits. Keep a deliberately edited valid ID in the draft and show that Save will apply it. If a staged deletion makes the toolbar's newly selected ID unavailable in the draft, require a replacement before Save. Cancel leaves any committed toolbar change in effect. On persistence failure, show the prior committed selection and surface the error. This is a single preference, with no per-tab model selection.

## Configuration record and editor

Keep preferences schema 2 and the existing serialized `defaultModelConfigurationID` key as the active ID. Keep language, appearance and typography. Reading preferences include optional-on-read `preferredReadingWidth`, `preferredCorrespondenceColor` and `skipDocumentSavePrompt` fields; absent values resolve to Wide, Amber and false. They use the same draft transaction, with no schema bump, model/credential reset or portable-document fields. Explicitly saved color choices remain respected. Add an optional-on-read `preferredTranslationDirection` field using the existing direction values. Persist the translation direction preference described in [interaction](interaction.md#input-and-task-lifecycle). Each configuration keeps a stable UUID from Add through Edit. Display these fields in order.

| Field | Editor contract |
| --- | --- |
| Vendor | OpenAI, Kimi, GLM or DeepSeek. Stored IDs are `openai`, `kimi`, `glm` and `deepseek`. The vendor selects the request profile independently of the URL. |
| Name | User-editable instance name. Suggest the selected model ID until the user supplies a name. Use the existing 128-character, trimmed single-line limit. Existing blank aliases continue to resolve to the model ID. |
| Model | Picker scoped to the vendor, with the dated catalog below and a **Custom Model ID…** option. Custom IDs remain trimmed, single-line, case-sensitive and at most 256 UTF-8 bytes. Existing IDs outside the featured list remain visible and selectable on Edit. |
| Reasoning Effort | Picker scoped to the vendor and exact model. Show documented levels and explicit Off where available. Show the provider default as Default. Unknown IDs offer Default only. |
| API Base URL | Prefill the vendor's canonical HTTPS API root. Allow a custom root and apply the local URL validation below. |
| API Key | Masked, configuration-scoped Keychain item. Keep existing Replace/Delete behavior. Saved configuration without a key is valid until dispatch. |

Use the existing uniqueness rule for the resolved name/effort pair. Two instances can share an API model, endpoint or key. Show effort and vendor/model details in the picker where needed to distinguish repeated names. A vendor change selects that vendor's suggested model and URL and clears the draft key. A model change retains a compatible explicit effort, otherwise visibly selects the recommended supported level or Default. Selecting a different model on the same vendor/URL can reuse that instance's existing key. An actual vendor change on an existing instance is a new credential binding even if the URL is identical. Revalidate the frozen vendor as well as the UUID and Base URL before undispatched work can read a key. Restoring the committed vendor and URL restores the original credential under the existing draft-intent rules.

Validate URLs locally: require a host and HTTPS; reject user information, query, fragment, whitespace/control characters and full operation suffixes such as `/chat/completions`, `/responses` or `/messages`. Preserve meaningful path and port; canonicalize scheme/host casing, default HTTPS port and a single trailing slash. Append relative `chat/completions` exactly once without discarding a base path. Reject malformed input rather than silently changing its API family. Do not follow HTTP redirects or derive credentials from URL text/environment settings.

Changing the Base URL clears the draft credential for that entry and requires re-entry before it can dispatch. It may still be saved without a key. This includes changing a path on the same host, because the path can select a different account product. Show that consequence in the editor. Restoring the committed vendor and exact URL before Save restores the original key state unless the user explicitly replaced/deleted it. Automatic endpoint clearing and an explicit Delete are distinct draft intents: an A→B→A round trip restores the original key without an extra key action, while an explicit Delete remains staged. A replacement entered for B survives reopening the editor and confirming unrelated edits at B; changing away from B invalidates that replacement. These rules apply across separate editor sheets before Settings Save. New endpoints require transmission acknowledgement keyed by provider and canonical origin, displaying the destination host; consent for OpenAI must not authorize an unrelated gateway.

Catalog order does not change saved configurations or the initial seeded records. Add chooses the suggested model and effort when the user chooses a vendor. GLM is a single vendor option. Use Standard API by default and retain previously saved custom URLs, including `https://open.bigmodel.cn/api/coding/paas/v4/`, as entered. The GLM Coding Plan URL can be entered manually with a matching eligible credential. Show a concise inline eligibility note for that official path. Zhipu directs self-built apps to its Standard API and limits subscription quota to supported environments. The Base URL selects the destination, and cannot establish entitlement. Preserve the path and consent boundary, use the configured product/key and surface any account error without fallback. Vendor compatibility, editable endpoint URL and model-specific effort are separate concerns. A single GLM vendor supports multiple URLs; a preset does not establish account eligibility.

## Effort capabilities and wire mapping

`auto` means provider/model default, not disabled reasoning. It omits graded `reasoning_effort`. `off` is an explicit request to disable reasoning; `on` enables binary thinking where no graded effort exists; `minimal` is the lowest graded level, offered only for models whose provider documents it. The model list uses Default, Off, On, Minimal, Low, Medium, High, Extra high and Max, with localized equivalents. For a known nonreasoning model, `auto` displays Not applicable and the editor disables effort selection.

Support the OpenAI, GLM, Kimi and DeepSeek capability entries below, including legacy entries used by existing configurations. Menus expose distinct documented settings for the selected model. Provider compatibility aliases that collapse to an existing level are represented by that level.

| Capability entry (checked 2026-11-05) | Allowed effort | v2 final body |
| --- | --- | --- |
| OpenAI `gpt-4.1-mini-2025-04-14` (deprecated; removal 2027-01-14) | `auto` only | Omit reasoning fields; `temperature: 0.2` |
| OpenAI `gpt-6-luna`, `gpt-6-sol`, `gpt-6.1-terra`, `gpt-5.6`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna` | `auto`, `off`, `low`, `medium`, `high`, `xhigh`, `max` | Off becomes `reasoning_effort: "none"`; a graded value is sent verbatim; Auto omits it. Omit sampling parameters for these reasoning entries, including when Auto is selected |
| OpenAI `gpt-6-astra`, `gpt-6.1-sol` | `auto`, `low`, `medium`, `high`, `xhigh`, `max` | Same graded mapping; Off is not offered because these models reject disabling reasoning |
| OpenAI `gpt-5.5`, `gpt-5.4`, `gpt-5.2` | `auto`, `off`, `low`, `medium`, `high`, `xhigh` | Same graded mapping; Max is not offered (these models top out at xhigh) |
| GLM `glm-4.7-flash`, `glm-4.7`, `glm-4.7-flashx`, `glm-5.1`, `glm-5`, `glm-5-turbo` | `auto`, `off`, `on` | Auto omits thinking controls; Off/On sets `thinking.type` to `disabled`/`enabled`; never send `reasoning_effort`; retain `temperature: 0.2` |
| GLM `glm-5.3`, `glm-5.3-flash`, `glm-5.3-flashx`, `glm-5.3-flashx-legal` | `auto`, `low`, `high`, `max` | Always `thinking.type: "enabled"`; send an explicit graded effort verbatim or omit it for Auto; omit sampling parameters. The provider default effort for these models is `max`, so Auto means the deepest reasoning |
| GLM `glm-5.2` | `auto`, `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` | Off sets `thinking.type: "disabled"` without graded effort; a graded value sets `thinking.type: "enabled"` and is sent verbatim; Auto omits both; omit sampling parameters. The provider documents mappings (low/medium to high, xhigh to max, minimal/none skip thinking); Bipara sends the displayed value verbatim and does not rewrite it |
| Kimi `kimi-k3.1-pro`, `kimi-k3.1-pro-highspeed`, `kimi-k3` | `auto`, `low`, `high`, `max` | Send explicit `reasoning_effort` verbatim. Auto omits it and defaults to Max. Omit `thinking` and sampling fields. |
| DeepSeek `deepseek-flash`, `deepseek-v4-pro` | `auto`, `off`, `low`, `high`, `max` | Off sends `thinking.type: "disabled"` without effort. Graded effort sends `thinking.type: "enabled"` and the selected `reasoning_effort`. Auto omits both and defaults to High. Omit sampling fields. |


The GLM-5.3 entries cannot disable thinking and do not offer Minimal, Medium, On or Extra high; `reasoning_effort` itself is GLM-5.2-or-later only. Do not copy OpenAI's effort menu or unrelated capability clamping into these entries. Unknown model IDs may be saved and attempted once with Auto under the chosen v2 profile; omit model-specific thinking/sampling fields, use the conservative reasoning budget below, and report unsupported capabilities without another request. Explicit effort for an unknown model requires adding a documented capability entry and tests first. Capability metadata is local code, not an editable generic parameter dictionary.


The final serialized HTTP request must retain the configured URL, exact model, mapped effort, profile-specific output mode, token-limit field/cap, exact canonical messages, no tools and non-streaming operation. OpenAI v2 binds canonical strict JSON Schema. GLM, Kimi and DeepSeek v2 bind JSON-object output and validate against the canonical schema locally. Use `kimi-json-v2` and `deepseek-json-v2` as the new versioned profiles. SDK/LangChain mutation is `unsupported_capability` before HTTP. Never send `reasoning_content` as translated text or include it in document/log output.

Reasoning uses output budget as well as answer text. For known nonreasoning models and explicit Off, v2 uses 8,192 translation / 2,048 alignment tokens; both legacy profiles keep their original 4,096/1,024. Enabled, graded, Auto reasoning and unknown v2 entries use initial total caps of 16,384 translation / 4,096 alignment tokens. These bounded engineering starting values require evaluation and do not establish quality or latency guarantees. OpenAI and Kimi send `max_completion_tokens`. GLM and DeepSeek send only `max_tokens`. [Kimi Chat Completions reference](https://platform.kimi.com/docs/api/chat), [DeepSeek Chat Completions reference](https://api-docs.deepseek.com/api/create-chat-completion/). Keep existing input, decoded-output, unit-text, deadline, concurrency and no-retry limits. A length finish remains `output_limit`; do not parse partial JSON or silently increase a cap.

Preserve `openai-json-schema-v1` and `glm-json-v1` for retained jobs and migration compatibility, including their original fixed sampling/reasoning parameters. Their exact legacy rules remain in model workflow. New configurations use v2 profiles. Model edits to a migrated entry select its appropriate v2 profile and apply only to new jobs.

## Runtime snapshots, credentials and portable documents

At job creation, capture configuration ID, provider/profile, model ID, effort, canonical Base URL and prompt versions. Freeze the endpoint/effort for every translation batch and correspondence operation belonging to that job, including background work, Retry and Resume. Add effort and the private runtime binding identity to correspondence cache identity; explicit rebinding clears cached model analysis. Changing the active model or editing a configuration never silently retranslates or changes an existing snapshot.

Before each new dispatch, resolve that configuration's key and require the saved configuration still to exist with the exact snapshot vendor and Base URL. Perform the entry/URL check and credential read within the same serialized Settings transaction boundary. A model/effort/alias edit at the same endpoint does not mutate the old job, which keeps its original model/effort. Key rotation at the same URL applies to later dispatches; an already dispatched request keeps its original key. Deletion, a changed vendor or a changed endpoint blocks later dispatches with local `configuration_unavailable`, preserves completed work, and sends no key/request. Existing HTTP work may finish. Local retained jobs never rebind to a changed endpoint. Resume requires restoration of the original configuration/endpoint; another service requires explicit Retranslate with replacement confirmation and destination consent. Never select a similarly named/newly created entry automatically.

Portable files persist requested provider/model/profile/effort and prompt attribution only. They exclude endpoint, display alias, local configuration ID, Keychain reference and credentials. After Open, reading/export remains offline. Before Resume or uncached phrase analysis, require an explicit session-local binding to an existing configuration matching provider/model/profile/effort. Show its display name and destination host: a file intentionally cannot prove its original endpoint. No matching configuration leaves model operations unavailable and offers configuration creation or explicit Retranslate. This applies both to the initial analysis attempt and to a binding sheet whose candidates disappear before confirmation; keep the coarse correspondence fallback while explaining the missing configuration and offering Settings, explicit Retranslate, or Cancel. Retranslate retains its separate replacement confirmation. An explicit binding is required even when the active model matches. Do not mark a document dirty merely for this private runtime binding. The file-version details live in document format.

## Preferences and Keychain migration

Use `dev.bipara.preferences.v2` for the new encoded record. If it exists but is corrupt/newer, report the problem and preserve data rather than fall back to v1/defaults. Only when it is absent, migrate a valid `dev.bipara.preferences.v1` record once:

1. Create a fresh UUID entry for each existing OpenAI/GLM record, preserving its exact model ID, and use the original hardcoded Standard API URL. Preserve the old effective request profile: OpenAI v1 with Auto, GLM v1 with Off. Do not upgrade models, change to Coding Plan or add recommended entries during migration.
2. Map the old default provider to its new entry, and preserve language, appearance and typography. Malformed/missing provider/default data must produce a recoverable migration error rather than silently choosing an unrelated entry.
3. Read only the two legacy provider-scoped Keychain items through the existing credential interface. Stage independent configuration-scoped copies, then persist/read back the complete v2 preferences record through the Settings transaction. A missing key remains missing. Serialize credential reads with this transaction.
4. On failure, compensate staged writes and leave v1 authoritative and readable; report compensation failures. On success, v2 becomes authoritative. Cleanup of superseded legacy keys/record follows only after verified v2 persistence; cleanup failure reports residue, retains v2 and retries cleanup independently without repeating migration or generating new IDs.

Existing v2 records retain IDs, provider, endpoint, credentials, model, effort and selection on upgrade. A missing translation direction decodes as Automatic. Preserve the existing seed entries and empty-list behavior. Feature the new catalog in Add/Edit only. A rollback build may lack the new profiles or preference field, so exercise upgrade with the new app and its paired worker. Opening an existing portable file retains its recorded attribution. Files with new profile IDs remain readable on versions that support unavailable attribution, with execution requiring a recognized matching profile. Verify these cases against the [acceptance plan](../testing.md#settings-and-provider-acceptance).
