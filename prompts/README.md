# Prompt Contract

These UTF-8 assets own prompt behavior and output schemas. Changes to prompts, examples, model parameters or repair behavior require a corresponding versioned design and evaluation update. Implementations load the canonical assets without silently rewriting them.

| Operation | System message | Output schema |
| --- | --- | --- |
| `translate` (new plain-text jobs) | [translation.v3.txt](translation.v3.txt) | [translation-output.v1.schema.json](translation-output.v1.schema.json) |
| `translate` (retained plain-text jobs) | [translation.v1.txt](translation.v1.txt), [translation.v2.txt](translation.v2.txt) | [translation-output.v1.schema.json](translation-output.v1.schema.json) |
| `align` | [alignment.v1.txt](alignment.v1.txt) | [alignment-output.v1.schema.json](alignment-output.v1.schema.json) |

Use exactly two model messages. Ordinary requests use the captured system asset verbatim. Single-unit recovery appends one LF and the [single-text.v1 directive](single-text.v1.txt) to that asset and uses the [single-text output schema](single-text-output.v1.schema.json). Both send a user message containing the JSON serialization of the operation's `input` object from [worker protocol](../docs/design/worker-protocol.md). Use UTF-8 with `ensure_ascii=False`; ordinary JSON escaping is required. Do not interpolate document strings into a template or system message. A LangChain prompt may bind one `{payload}` variable to the already serialized JSON string; the system asset is a literal `SystemMessage`, not a format template containing JSON braces.

Serialize these logical messages as Responses `input`, Messages top-level `system` plus user `messages`, or retained Chat Completions `messages`, without changing asset/payload text. Use a fresh invocation with no conversation history, memory, tools, search, or retrieval. Never include the API key, local path, clipboard metadata, tab title, app language, appearance, or UI state in a model message. App interface language is independent of translation direction.

Output schemas are deliberately a small JSON Schema subset compatible with the selected OpenAI structured-output profile. They describe shape. [Model workflow](../docs/design/model-workflow.md) additionally requires exact ID coverage, canonical results in request order, UTF-8 budgets, nonempty values, legal statuses, literal quote resolution, and range/meaning checks. Shape validation does not establish translation quality or semantic alignment.

New plain-text jobs use `translation.v3`. Alignment uses `alignment.v1`. Versioned prompt files are runtime assets, not a changelog. All plain-text versions use the v1 batch output schema for ordinary requests. Package these assets from this directory; do not maintain a second edited copy in Swift/Python source. Both worker bundles take their runtime inventory from [`ASSET_FILES`](../Worker/bipara_worker/assets.py). Build and release checks compare each bundled file and the hash manifest with these canonical assets. Saved jobs keep their recorded translation instructions on every batch, Retry and Resume. Only a single-unit recovery request appends the recovery output contract. Explicit Retranslate captures the current version. A semantic prompt/schema change creates a new version and requires a new provider evaluation; it must not mutate a running job or silently reinterpret a saved one. Mechanical packaging must preserve asset bytes.

V2 makes logical scope, complete clauses/enumerations, and protected technical syntax explicit. Natural-language headings, labels and descriptive values are translated; configuration keys, identifier values, executable code and Markdown syntax remain literal. Plain text describes each output string, not permission to strip markup. Paragraph separators and outer indentation remain application-owned. A silent comparison within the same response checks conditions, omissions and literals without adding another model call or output field.

Plain-text v3 and Markdown v4 use context to resolve the meaning of a phrase, preserve the conditions of an instruction, and retain deliberate imagery. Exact names used for lookup, invocation or deriving a key or filename keep their source spelling. Descriptive labels are translated. A brief rendering may accompany an exact name when its meaning also matters and the format permits.

[cases.json](cases.json), corpus version 6, contains 22 plain translation, six Markdown translation and six alignment cases with original synthetic inputs, valid example outputs, and review expectations. T07–T10 cover logical scope and fragments; T11–T14 cover omissions and distinctions; T15–T20 cover frontmatter, Markdown, links, code and configuration. T21 and T22 cover a shipment stamp and literary imagery. `literal_checks` specify exact literal, prefix, substring or occurrence-count invariants per unit. Logical truth tables and `semantic_checks` require review of actual translations. Example outputs establish an admissible shape and meaning, not an exact-string oracle for a live model. Do not send these examples in ordinary production calls. Test transport with their fixed outputs, and evaluate live responses using the specified semantic checks.

Prompt fixtures use short readable unit IDs. When exercising the application IPC, map them to deterministic UUIDs in both the input and expected output; keep the case ID separately. This preserves the same prompt case without weakening the protocol's identity validation.

Each worker operation makes one model call at most. The app schedules bounded [unit recovery](../docs/design/model-workflow.md#failure-and-retry-policy). Validation failure returns a typed error; uncertain correspondence returns a labeled larger match. Offline fixture tests validate packaging, dispatch and sample invariants; they do not establish that a provider follows the instructions. The separate [translation prompt checks](../docs/testing.md#translation-prompts) own live semantic acceptance.

The [validation status](../docs/validation.md) records executed offline/build evidence and pending live acceptance.

## Markdown translation asset

The current [v4](translation.markdown.v4.txt) and retained [v3](translation.markdown.v3.txt) prompts permit inline code to move with translated clauses between the same consecutive formatting boundaries, including inside a single emphasis span or link label. Saved jobs using [v2](translation.markdown.v2.txt) allow this only in code-and-prose units. [V1](translation.markdown.v1.txt) preserves order throughout. All four versions specify the inline Markdown operation and use the existing translation output schema. The worker checks the unit kinds, hard-break counts, output shape and byte limits. Swift checks protected inline literals and reconstructed document structure before commit. M01 exercises emphasis, links and a hard break. M02 exercises a reference link and an escaped table-cell delimiter. M03 exercises a fronted condition with four byte-identical code spans. M04 reorders a toolkit and command before a separate emphasized phrase. M05 and M06 cover a printed index title alongside descriptive link text and a weighing instruction in the reverse direction. The opt-in live Markdown checks are specified in [MD-12](../docs/testing.md#markdown-acceptance).
